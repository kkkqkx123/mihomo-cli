# Mihomo CLI - Project Context Documentation

## Project Overview

Mihomo CLI is a non-interactive management tool for the Mihomo proxy core. This tool provides comprehensive management capabilities over the Mihomo RESTful API via a command-line interface (CLI), delivering a stateless and scriptable proxy management solution.

### Project Goals

- Provide a pure command-line interface for Mihomo management without requiring a GUI.
- Support automated scripting and batch operations.
- Decouple from the Mihomo core process to enhance stability.

### Core Features

- **Stateless Design**: The CLI does not persist runtime state; all state queries are performed in real-time against the API.
- **Configuration Persistence**: API address and Secret are saved to a local configuration file to avoid repeated input.
- **Query vs. Mutation Separation**: Distinct operations for querying (`get`, `list`, `show`) and modifying (`set`, `switch`, `update`).
- **Controllable Output Format**: Supports both Table and JSON output formats for human readability and script parsing.

## Technology Stack

### Project Architecture

- Modular design following standard Go project structures.
- Command tree architecture based on Cobra.
- Layered design: `cmd` (Command Layer) → `internal` (Business Logic Layer) → `pkg` (Common Types Layer).

## Build & Run

### Usage

```bash
# build
./deploy/build.sh

# Initialize configuration
./mihomo-cli config init

# Query current mode
./mihomo-cli mode get

# List proxies
./mihomo-cli proxy list

# Switch proxy node
./mihomo-cli proxy switch Proxy NodeName

# Test latency
./mihomo-cli proxy test Proxy

# Auto-select fastest node
./mihomo-cli proxy auto Proxy

# JSON format output
./mihomo-cli proxy list -o json
```

## Deployment

All deployment assets live in `deploy/`. No config is loaded from the current directory or the repository root.

- `deploy/build.sh`: builds `mihomo` core and `mihomo-cli` into `build/`.
- `deploy/install.sh`: orchestrates build, config init, and service setup:
  - `--build` / `--no-build`: build binaries (auto-builds when `build/mihomo-cli` is missing).
  - `--service` / `--no-service`: install the system service (Linux systemd; other platforms print manual steps).
  - `--enable-autostart`: enable boot autostart, requires `--service`; user-level services also need `loginctl enable-linger`.
  - `--system`: system-wide service (needs root); default is user-level service.
  - `--force`: overwrite existing config files.
- Config sources:
  - CLI connection config is generated by `mihomo-cli config init` into the user config dir.
  - `deploy/config.toml.example` is copied to the user config dir as `config.toml`, or pointed to with `--toml`.
  - `deploy/mihomo-config.yaml.example` is copied to `~/.config/mihomo/config.yaml` (user service) or `/etc/mihomo/config.yaml` (system service), or pointed to with `--path`.
- Service model: `mihomo-core.service` runs the `mihomo` kernel directly (`Type=simple`), with the core config as the single source of truth. `mihomo-cli` is not part of the service process; it is a stateless API client and must not daemonize the kernel for service deployments.

### System Service Usage

`deploy/install.sh --service --enable-autostart` installs `mihomo-core.service`. The unit runs the kernel directly; lifecycle operations always go through `systemctl`, never through `mihomo-cli start/stop`.

**User-level service (default):**

- Unit: `~/.config/systemd/user/mihomo-core.service`
- Binary: `~/.local/bin/mihomo`
- Config and data: `~/.config/mihomo`

```bash
systemctl --user start mihomo-core.service
systemctl --user stop mihomo-core.service
systemctl --user restart mihomo-core.service
systemctl --user status mihomo-core.service
journalctl --user -u mihomo-core.service -f
```

Autostart:

- Login autostart: `systemctl --user enable mihomo-core.service`.
- Boot autostart: Linux user services also require lingering:
  `sudo loginctl enable-linger $USER`.
  Without lingering, the service starts only after the user logs in.

**System-level service (`--system`, requires root):**

- Unit: `/etc/systemd/system/mihomo-core.service`
- Binary: `/usr/local/bin/mihomo`
- Config and data: `/etc/mihomo`

```bash
sudo systemctl start mihomo-core.service
sudo systemctl stop mihomo-core.service
sudo systemctl restart mihomo-core.service
sudo systemctl status mihomo-core.service
sudo journalctl -u mihomo-core.service -f
```

`--enable-autostart` enables the unit; no lingering is needed for system-level services.

**Operating notes:**

- The unit executes `mihomo -d <config-dir> -f <config-dir>/config.yaml` with `Restart=on-failure` and journal logging. Do not replace it with `mihomo-cli start`.
- `mihomo-cli status` queries the API and works for service-managed instances; when running locally it also reports the PID and systemd unit (`-o json` for scripts). `mihomo-cli start/stop` are only for ad-hoc instances; `start` refuses to launch while the API port is already in use, preventing duplicate cores.
- Change the core configuration, then reload or restart the unit (`systemctl --user reload mihomo-core.service` for user-level, `sudo systemctl reload mihomo-core.service` for system-level). Do not put proxy settings into the unit file.
- The `mihomo-cli service` subcommand is Windows SCM-specific; on Linux use `systemctl`.
- Verify connectivity through an explicit proxy environment, not system proxy or TUN:

```bash
export http_proxy=http://127.0.0.1:7890
export https_proxy=http://127.0.0.1:7890
curl -sS -o /dev/null -w '%{http_code}\n' https://www.gstatic.com/generate_204
```

- TUN and system proxy remain disabled unless explicitly enabled in the core configuration.

## Core Design Principles

### 1. Stateless

- The CLI does not persist runtime state.
- All state queries are performed in real-time against the API.
- Prevents state synchronization issues.

### 2. Configuration Persistence

- API address and Secret are saved to a local configuration file.
- Eliminates the need to input sensitive information repeatedly.
- Configuration files are stored in the user directory with appropriate permissions.

### 3. Query vs. Mutation Separation

- **Query Operations**: `get`, `list`, `show`.
- **Mutation Operations**: `set`, `switch`, `update`.
- Ensures clear semantics and distinct exit codes.

### 4. Controllable Output Format

- Supports both Table and JSON formats.
- Facilitates both human reading and script parsing.
- Unified output format specifications.

### 5. Permission Management

- Windows SCM service installation requires Administrator privileges.
- Linux user-level systemd services do not require admin; system-level installation (`--system`) requires root.
- System proxy modification requires Administrator privileges.
- Provides clear permission error messages.

### 6. Unified Output Formatting

- All output must use `internal/output` module, never use `fmt.Print*` or `github.com/fatih/color` directly.
- **Status messages**: Use `output.Success()`, `output.Error()`, `output.Warning()`, `output.Info()`.
- **Plain output**: Use `fmt.Fprintf(output.GetGlobalStdout(), ...)` for stdout, `fmt.Fprintf(output.GetGlobalStderr(), ...)` for stderr.
- **JSON output**: Use `output.PrintJSON(data)` when `-o json` flag is set.
- **Table output**: Use `output.NewTable()` for table formatting.
- This ensures consistent output style, proper stdout/stderr separation, and easy global output redirection.
