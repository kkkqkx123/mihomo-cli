# CLI 配置加载问题清单

现状涉及两套配置文件：`config.yaml`（CLI 连接配置，由 Viper 驱动）和 `config.toml`（被托管 Mihomo 内核配置，由 BurntSushi TOML 驱动）。两者复用 `APIConfig` 结构体但查找、加载、校验路径完全独立。

## 加载链路

* 启动链路为 `cobra.OnInitialize(initConfig)` 加 `PersistentPreRunE(preRun)` 内再次调用 `initConfig`，两次初始化全局 Viper。
* `ConfigManager.InitViperConfig` 负责设置 Viper 默认值、选择配置文件、启用环境变量、前缀匹配和读取文件，随后 `root.go` 用命令行标志做覆盖。
* 业务命令大多直接读取 Viper 中的 `api.address`、`api.secret`、`api.timeout` 来创建 API 客户端，不经过结构体反序列化与校验。
* 仅输出流初始化和 `config set` 会走 `LoadCLIConfigFromViper` 的反序列化加校验。
* `Loader.Load` 使用私有 Viper 实例，生产代码基本不用；`config show` 读取的是 TOML 而非 YAML。

## 已确认的问题

### 命令行覆盖逻辑错误

* 超时标志默认值为 10 且判断条件为非零即覆盖，导致文件中的超时值恒被覆盖。
* 标志与配置文件、环境变量的优先级未明确绑定，环境变量对嵌套键基本不可用。
* 初始化执行两次，浪费且易造成状态不一致。

### 子命令行为分裂

* `config init` 与 `config set` 写 YAML，`config show` 读 TOML，展示与实际写入不一致。
* `config set` 与 `config init` 无视全局 `--config` 路径，恒写默认路径。
* `config set` 仅支持三个键，代理测速与输出相关键无法通过命令维护。
* `config set` 在加载失败时直接回退到默认配置，可能丢弃文件中其他已有配置。

### 读写不对称与持久化缺陷

* 保存逻辑漏写代理批大小与最大节点数，一次保存即丢失字段。
* 保存依赖私有 Viper 实例的写入方法，与全局 Viper 读取路径不一致，覆盖语义不透明。
* 保存与加载过程夹带输出日志副作用，不利于测试与复用。
* 密钥以明文保存，文件与目录权限偏宽松，非原子写入。

### 校验缺位

* 热路径绕过校验，非法地址到发起请求时才暴露，报错滞后。
* 代理批大小、最大节点数与部分输出组合缺少校验。
* 缺文件、非法文件的语义在三处加载入口不一致，有的报错有的静默回退。

### 默认值与路径重复

* 默认值在默认配置函数、Viper 初始化、TOML 默认三处重复，易漂移。
* 基础目录解析在路径集合与路径解析器中重复，部分目录查询只有一边提供。
* 配置包依赖输出包的类型，层次不够干净。

## 影响

* 用户修改超时不生效，排查困难。
* 查看与设置看到的不是同一份配置，容易误判。
* 指定 `--config` 后部分命令不生效。
* 非法配置文件难以及时发现，修复路径不顺畅。
* 含密钥的配置文件权限与写入可靠性不足。
